# Контракт app-server, на который опирается код

Проверено на `codex-cli 0.152.1`, `0.153.0-alpha.5` и `0.160.1`. Контракт
версионный: после обновления Codex схему надо перегенерировать и сверить, а не
надеяться.

Сверка 0.160.1 против 0.152.1, 06.10.2026: все методы и поля, которые шлёт duo,
на месте. Добавились четыре запроса сервера. На
`item/permissions/requestApproval` duo отвечает пустым разрешением со
`scope: turn`. Три других — `item/tool/call`, `attestation/generate`,
`account/chatgptAuthTokens/refresh` — для duo недостижимы: он не регистрирует
динамические инструменты, не объявляет аттестацию и не управляет токенами
ChatGPT. Запросы duo и его ответы тесты проверяют по фикстуре схемы, см. ниже.

Сверка 0.153.0-alpha.5 против 0.152.1, поле за полем: добавился один метод
`plugin/reconcile`; `ThreadStartParams`, `TurnStartParams`, `SandboxMode`,
`AskForApproval`, `Personality`, `ThreadHistoryMode`, `ThreadSetNameParams`,
`TurnStatus`, весь набор уведомлений и весь набор запросов сервера — без
изменений. Список проверенных версий живёт в `VERIFIED_CODEX_VERSIONS`, и
`verify` ругается на всё, чего в нём нет.

```bash
CODEX=/Applications/ChatGPT.app/Contents/Resources/codex-cli/bin/codex
"$CODEX" app-server generate-json-schema --experimental --out /tmp/codex-proto
"$CODEX" app-server generate-ts        --experimental --out /tmp/codex-proto-ts
```

`--experimental` обязателен: без него экспериментальные методы и поля просто
вырезаются из вывода, и схема выглядит меньше, чем есть.

Тесты проверяют запросы duo и его ответы на запросы сервера по фикстуре
`tests/schema/<версия>/`. Это файлы вывода генератора, скопированные без
изменений, — только те, чьи контракты проверяются; каталог сам и есть их
список. Для новой версии — сгенерировать во временный каталог, скопировать те
же пути и поменять `SCHEMA` в `tests/test_duo.py`:

```bash
OUT=$(mktemp -d); "$CODEX" app-server generate-json-schema --experimental --out "$OUT"
(cd tests/schema/0.160.1 && find . -name '*.json') | while read -r f; do
  mkdir -p "tests/schema/NEW/$(dirname "$f")" && cp "$OUT/$f" "tests/schema/NEW/$f"; done
```

## Транспорт

`codex app-server --listen stdio://`, JSON-RPC 2.0 по строке на сообщение.
На стандартном выводе три вида сообщений, и все три обязательны к обработке:

| Вид | Признак | Что делать |
|---|---|---|
| ответ | есть `id`, нет `method` | сопоставить с запросом |
| уведомление | есть `method`, нет `id` | обработать и продолжить |
| **запрос сервера** | есть и `method`, и `id` | **ответить**, иначе ход встанет |

Третий — единственная неочевидная часть. Сервер блокируется, пока клиент не
ответит. `appserver.py` отвечает на всё: отказом на одобрения, временем на
`currentTime/read`, ошибкой `-32601` на незнакомое.

## Порядок вызовов

```
initialize   {clientInfo:{name,version,title?}, capabilities:null}
initialized  — уведомление, без params вообще (в схеме у него только method)
thread/start {cwd, ephemeral:false, [sandbox, approvalPolicy — только по флагу, иначе из config.toml], model,
              developerInstructions — роль оппонента}  -> {thread:{id}, ...}
turn/start   {threadId, input:[{type:"text",text,text_elements:[]}],
              model, effort, serviceTierForTurn, outputSchema,
              additionalContext:{duo.phase, duo.format}}
                                              -> {turn:{id, status}}
thread/name/set {threadId, name}              -> {}
```

Любой запрос до `initialize` получает `Not initialized`. Повторный
`initialize` — `Already initialized`.

Продолжение в новом процессе: `thread/resume {threadId}` **до** `turn/start`.
Три варианта резюма — по `threadId`, по `path`, по `history`; приоритет
`history > path > threadId`. Нам нужен только `threadId`.

## Что измерено на реальных ходах

- `gpt-5.6-sol`, `max`, бриф 11 КБ с чтением репозитория: раунд 1 — 13 142
  символа ответа; раунд 2 прерван бюджетом 1500 с после ~120 действий, включая
  `contextCompaction`. Отсюда модель таймаута: не настенные часы, а тишина —
  рабочий ход стримит события непрерывно, зависший молчит. `--idle-timeout`
  900 с, жёсткого потолка по умолчанию нет.
- `thread/turns/list` на `0.153.0-alpha.5` отвечает и при `capabilities: null`,
  без `experimentalApi: true` — вопреки docs. Проверено двумя вызовами подряд с
  разными capabilities на одном треде. Включать флаг всё равно безопасно.
- Прерванный ход остаётся в истории со `status: interrupted` и всем, что успел
  накопить; сообщение пользователя уже в треде, повторная отправка — дубликат.

## Восстановление хода по `clientUserMessageId`

`turn/start` принимает `clientUserMessageId`; история (`thread/turns/list`,
`itemsView: "full"`, `sortDirection: "desc"`) возвращает его как
`userMessage.clientId`. Это единственный способ узнать судьбу хода, чей ответ
процесс не увидел: совпал `clientId` — ход принят, `status` говорит, чем
кончился; не совпал или хода нет — отправлять заново под тем же id безопасно.
`thread/resume` побочных эффектов не имеет и годится как discriminator
«есть ли роллаут». Если же он отвечает «чужой writer», из этого **нельзя**
заключить, что ход не принят: сначала `thread/fork`, потом тот же поиск по
`clientId` в истории форка — форк уносит принятый ход с собой.

## Завершение хода

Уведомления `turn/failed` **нет**. Провал приходит как `turn/completed` с
`turn.status`, а статусов четыре: `completed`, `interrupted`, `failed`,
`inProgress`. Текст ошибки — в `turn.error`.

Неизвестно и не стоит закладываться, отвечает ли `turn/start` сразу или только
по завершении хода. `appserver.py` сначала ждёт ответ, потом — терминальный
статус; если статус уже пришёл, второе ожидание завершается мгновенно.

Финальный текст: элементы `agentMessage`. Поле `phase` различает `commentary` и
`final_answer`, но схема прямо предупреждает, что провайдеры выставляют его
непоследовательно и отсутствие надо считать «фаза неизвестна». Поэтому: сначала
последний `final_answer`, иначе последний любой.

`turn/completed` несёт весь список `turn.items` — он достовернее накопленных
потоковых `item/completed`, и код предпочитает его.

## Видимость треда в sidebar

Четыре условия, каждое ломается молча:

1. `ephemeral: false`. Ephemeral-тред живёт в памяти и не попадает никуда.
2. Настоящий первый ход. Один `thread/start` не создаёт даже файла роллаута, а
   тред с пустым `preview` отфильтровывается из любого списка.
3. Интерактивный источник сессии. Подкоманда `codex app-server` проставляет
   `VSCode` — он в списке интерактивных. `codex exec` проставляет `Exec` — его
   там нет, поэтому exec для этой задачи не годится.
4. При чтении списка — `modelProviders: []` явно. С опущенным полем выдача
   молча сужается до текущего провайдера по умолчанию.

Даже когда все четыре выполнены, Desktop узнаёт о чужом треде только при
следующем чтении списка: уведомления рассылаются подписчикам своего экземпляра
app-server. На macOS список перечитывает `open "codex://threads/<id>"`.

## Одновременная запись

Paginated-тред держит одного писателя на все процессы. Второй получает `-32600`
с упоминанием writer. Отсюда решение не держать долгоживущее соединение: процесс
на вызов.

Измерено 03.09.2026: как только Desktop загружает тред — например по deep link
`codex://threads/<id>` — его собственный app-server (дочерний процесс
ChatGPT.app) берёт `thread-writer-locks/<id>.lock` и **не отдаёт**: ни через
45 секунд ожидания, ни после переключения Desktop на другой тред. Отдаёт только
перезапуск Desktop. Выход — `thread/fork {threadId, cwd, ephemeral:false, …}`:
он копирует историю в новый тред, который никто не держит; `duo` делает это
сам при `-32600` с упоминанием writer, пишет `forked_from` в state, а исходный
берёт в `archive_debt` — заархивировать удерживаемый тред нельзя тем же
`-32600`. Измерено 04.09.2026: человек открыл тред между фазами
`design` и `review`, что естественно, — и без форка ревью не запустилось бы.

По исходнику `rust-v0.160.1` блокировка — файловая блокировка ОС в процессе,
где тред загружен. Её снимают выгрузка треда (нет подписчиков и простой, по коду
60 секунд) и выход процесса; `thread/fork` блокировку источника не берёт.
Измерено 06.10.2026 на 0.160.1: Desktop открыл тред по deep link, duo форкнул
его и Desktop переключили на другой тред. Архивация исходника получила
`-32600` и через 105 секунд после переключения, и через 9,5 минуты. `lsof` на
lock-файл показал держателя: app-server внутри ChatGPT.app, один процесс с
запуска приложения в 11:35. Он держал блокировки семи тредов, загруженных в
Desktop за день. Время изменения lock-файла обновляется при захвате, и самую
старую из этих блокировок Desktop взял в 12:21 — к проверке в 20:38 прошло
больше восьми часов. Выгружает ли Desktop тред когда-нибудь сам, не
измерено; снимает блокировку перезапуск Desktop, как в замере 03.09.

Измерено 05.09.2026 на 0.153.4, и это меняет цену форка. Свежий форк **не
появляется** в `thread/list`: ни в живых, ни в архивных, ни до `thread/name/set`,
ни после. При этом `thread/resume` на нём проходит, а `thread/turns/list`
возвращает всю историю источника с теми же `clientId` — то есть восстановление
принятого хода через форк работает, а видимой строки в sidebar форк не занимает,
пока не сделает собственный ход. Поле `forkedFromId` в схеме есть, но в этом
сторе оно пустое у всех тредов, включая только что созданный форк.

Повторено 06.10.2026 на 0.160.1: форк без собственного хода в `thread/list` нет
ни до `thread/name/set`, ни после; ответ `thread/fork` с `excludeTurns: true`
приходит без ходов, а `thread/turns/list` отдаёт всю историю источника.

Отсюда два следствия. Падение между ответом `thread/fork` и записью id не
оставляет ничего видимого — то же ослабленное окно, что и у `thread/start`, и
зачищать нечего. И искать «свой» форк перебором `thread/list` по имени или
времени нельзя: единственное, что такой перебор находит, — форк, который человек
сделал сам, а архивировать чужой тред хуже, чем не убрать свой.

`thread/list` отдаёт страницы: `nextCursor` возвращается вместе с `data`, а
`createdAt` и `updatedAt` — Unix-секунды, целым числом, не ISO. Потребитель,
читающий только первую страницу, видит примерно половину тредов.

## Формат ответа

`outputSchema` заставляет весь финальный ответ быть JSON — и ровно это видит
человек в окне Desktop: `{"confidence":"high","findings":[...`. Для читаемого
треда ответ должен быть прозой. Отсюда формат `trailer` по умолчанию: проза,
затем один блок ```json с вердиктом, без `outputSchema`; контракт формата идёт
с каждым ходом в `additionalContext` `duo.format`. Разбор берёт **последний**
fenced-блок, потому что проза может цитировать JSON раньше. Формат `json`
оставлен для слабых моделей, которые контракт не держат.

|---|---|---|

| `item/fileChange/requestApproval` | `decision` | `decline` |

`SandboxMode`: `read-only`, `workspace-write`, `danger-full-access`.
`AskForApproval`: `untrusted`, `on-request`, `never` либо объект `{granular:…}`.

## outputSchema

`turn/start` принимает `outputSchema` — «JSON Schema, ограничивающая финальное
сообщение ассистента для этого хода». Схема проверяется строго, поэтому в
`verdict.py` каждое свойство перечислено в `required`, у каждого объекта стоит
`additionalProperties: false`, а числовых границ нет вовсе. Тест
`test_every_property_is_required` следит, чтобы это не разъехалось.

## Блокировки: реестр рядом с ядром

`flock` знает, кто держит ключ, но код об этом не знает — и за восемь раундов
ревью запись трижды уезжала на ключ вне захваченного набора, каждый раз из
нового вызывающего. Поэтому `state.py` ведёт реестр ключей, которые процесс
держит прямо сейчас: он заполняется внутри `SessionLock.__enter__`, там же, где
берётся `flock`, и очищается в `__exit__`.

`migrate` начинается с `require_held(src_key, dst_key)` и требует блокировку на
цель пересылки, прежде чем последовать редиректу. Перенос физически не может
записать незахваченный ключ, каким бы ни был вызывающий. Это единственное
место, где инвариант проверяется: `save` этого не требует, потому что состояние
пишут и без блокировки — в тестах и при первой записи.

## Проекты Desktop и каталог треда

Измерено 07–08.09.2026 на 0.153.4. В базе app-server есть `projects` и
`project_roots`, у треда — поле `projectId`, но ни у одного из 618 тредов оно
не проставлено. `thread/list` с фильтром `cwd` возвращает только точное
совпадение, а `project/list` отдаёт корни проектов, хотя в опубликованной
v2-схеме его нет. При этом в sidebar под проектом показан тред, чей `cwd` лежит в подкаталоге
корня, то есть точный корень не нужен. Похоже на группировку по
префиксу, но это вывод из одного наблюдения: тред с `cwd` в scratchpad
`/private/tmp/…` там же, и префиксом это не объясняется — возможно, его
перенесли руками. Алгоритм sidebar не подтверждён. Подмена `cwd` на корень,
сделанная 07.09, всё равно была лишней: она расширяла рабочую область Codex до
всего корня проекта, ничего не гарантируя. 08.09 убрана.

Настоящая причина «не того проекта» — не Desktop, а `$PWD`: рабочий каталог
shell в Claude уплывает после `cd`, и в 23 из 56 транскриптов на этой машине
он менялся по ходу чата. Каталог чата — первая запись транскрипта с
верхнеуровневым `cwd`; во всех 56 она совпадает с каталогом, под которым
транскрипт лежит. Поле приходит с первой записью `user`, третьей–девятой
строкой, однажды в записи `system` — первую строку файла читать нельзя.

`thread/name/set` работает и на треде под чужим writer-lock, поэтому имя
синхронизируется каждый настоящий раунд без сравнения с состоянием: состояние
не видит переименования в Desktop.

## Фаза и формат идут с каждым ходом

Измерено чтением исходника `rust-v0.160.1` 06.10.2026. `developerInstructions`
доходят до модели только при полной сборке контекста: на свежем треде, после
сжатия, в новом окне. Возобновлённый тред восстанавливает прежние сообщения из
rollout и держит старые инструкции, что бы ни передал `thread/resume`. Поэтому
в инструкциях треда только роль оппонента — она одна на все фазы, — а фаза и
формат ответа идут в каждом `turn/start` двумя записями `additionalContext` с
`kind: application`: `duo.phase` и `duo.format`. Сервер превращает их в
сообщения с ролью developer.

Сервер помнит последнюю карту и шлёт запись, только если она изменилась. Duo
держит процесс на один раунд, после холодного возобновления карта пустая, и обе
записи уходят каждый раунд и остаются в истории — около 2,5 КБ за раунд.
Поэтому каждая начинается фразой, что она заменяет прежние указания duo о том
же. Значение длиннее 4000 байт UTF-8 сервер режет посередине; тест держит обе
записи в этом бюджете.
